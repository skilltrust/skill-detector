## False positives found

### FP-1: SD-013 CRITICAL fires on brainstorming threat-model table

- **Rule**: SD-013 (Persistence Mechanism)
- **Target**: skill-detector (self)
- **File**: `_bmad-output/brainstorming/brainstorming-session-2026-03-17-200500.md:54`
- **Finding**: `shell profile modification detected — persistence mechanism` (CRITICAL, HIGH confidence)
- **Actual content** (line 54): `- Could it modify files outside project directory (~/.ssh, ~/.zshrc, ~/.gitconfig)?`
- **Why it's a FP**: This is a threat-model brainstorming document written by the AI assistant, listing questions about what a malicious skill *could* do. The string `~/.zshrc` appears in a question, not as an instruction. The file is in `_bmad-output/` (AI-generated planning docs), not in a skill or hook.
- **Impact**: Drives the Security axis to **F** (CRITICAL) on the self-scan, which looks alarming to any reviewer checking the project's own report.
- **Proposed fix**: SD-013 should reduce confidence to LOW when the matched line is inside a markdown list item that reads as a question (starts with `- Could it`, `- Does it`, `- Would it`, etc.). Alternatively, exclude `_bmad-output/` and similar AI-session-log directories from scanning by default.

### FP-2: SD-004 HIGH fires on brainstorming threat-model table

- **Rule**: SD-004 (Credential Access)
- **Target**: skill-detector (self)
- **File**: `_bmad-output/brainstorming/brainstorming-session-2026-03-17-200500.md:235`
- **Finding**: `access to credential path ~/.env` (HIGH confidence)
- **Actual content** (line 235): `| Broken Access Control | Reading ~/.ssh, ~/.aws, ~/.env, credential paths | Critical |`
- **Why it's a FP**: This is a Markdown table cell in a threat-taxonomy document, listing threat categories for review. The mention of `~/.env` is documentary, not operational.
- **Impact**: Drives the Permission Hygiene axis to **F** (CRITICAL) on the self-scan.
- **Proposed fix**: Same as FP-1 — reduce confidence to LOW when matched string is inside a Markdown table cell (`| … |` context) or a bullet-question pattern. A two-signal corroboration rule (e.g., credential path mention + an actual file-read command on the same or adjacent line) would eliminate this class of FP.

### FP-3: SD-012 HIGH fires on brainstorming doc "post-install scripts" mention

- **Rule**: SD-012 (Post-Install Hook)
- **Target**: skill-detector (self)
- **File**: `_bmad-output/brainstorming/brainstorming-session-2026-03-17-200500.md` (3 hits: lines 68, 243, 306)
- **Actual content examples**:
  - Line 68: `- Could it include silent post-install scripts?`
  - Line 243: `| Integrity | Post-install scripts / hooks | Medium |`
  - Line 306: `- Script injection (post-install, cron, CI/CD modification)`
- **Why it's a FP**: Same pattern as FP-1/FP-2 — the term "post-install" appears in threat documentation, not in an actual `package.json` lifecycle hook.
- **Proposed fix**: SD-012 should be file-type aware. When the file is `.md` (not `package.json`, `package-lock.json`, or a shell script), require a code-block or JSON-structure context before flagging. A plain sentence mentioning "post-install" in prose is not a hook definition.

### FP-4: SD-007 HIGH fires on README.md badge URLs and CONTRIBUTING.md repository links

- **Rule**: SD-007 (Outbound Network Call)
- **Target**: skill-detector (self)
- **Files**: `README.md` (8 hits), `CONTRIBUTING.md` (1 hit), `docs/development-guide.md` (3 hits)
- **Example findings**:
  - `outbound network reference to https://img.shields.io/github/actions/workflow/status/…` (README.md:3)
  - `outbound network reference to https://github.com/velzepooz/skill-detector.git` (docs/development-guide.md:16)
  - `outbound network reference to https://semver.org` (docs/development-guide.md:191)
- **Why it's a FP**: Standard Markdown documentation legitimately contains badge images, install links, clone URLs, and reference links. None of these cause the AI agent to make network calls — they are hyperlinks a human clicks.
- **Severity mismatch**: Rated HIGH. Shield badges and GitHub links driving a HIGH finding is misleading.
- **Proposed fix**: SD-007 confidence should be LOW for `.md` files unless the URL appears inside a code fence (```bash curl…```) or in an explicit skill instruction context. Alternatively, add a known-safe domain allowlist: `shields.io`, `github.com/*/releases`, `semver.org`, `pkg.go.dev` etc.

### FP-5: SD-007/SD-008 flood from `package-lock.json` and `node_modules/`

- **Rule**: SD-007 (Outbound Network Call), SD-008 (Base64 Obfuscation)
- **Target**: skillmoss-go (88 SD-007 hits + 63 SD-008 hits from `package-lock.json` alone; plus 506 hits from `node_modules/`)
- **Why it's a FP**: `package-lock.json` contains registry URLs (`https://registry.npmjs.org/…`) and package integrity hashes (base64 SHA-512). These are not agent instructions — they are dependency metadata. `node_modules/` READMEs contain badge links. No skill or AI agent reads `package-lock.json` as an instruction source.
- **Impact**: Drives skillmoss-go's Security axis to **D** with the reported finding being a npmjs.org registry URL — indistinguishable from a real exfiltration URL in the summary line.
- **Proposed fix (most impactful in the whole pass)**: Add `package-lock.json`, `package.json` (registry `resolved` fields), and `node_modules/**` to the default exclusion list. These are dependency artifact files, not AI configuration. This single fix would eliminate ~500 FP findings from the skillmoss-go scan.

### FP-6: SD-003 HIGH fires on `.claude/skills/*` internal navigation paths

- **Rule**: SD-003 (Path Traversal)
- **Target**: skill-detector (self)
- **Files**: ~30 files in `.claude/skills/**/*.md` and `.codex/skills/**/*.md`
- **Example finding**: `path traversal pattern detected — access outside skill directory` on `../resources/compression-rules.md` in `.claude/skills/bmad-distillator/agents/distillate-compressor.md:7`
- **Actual content**: `You must load and apply '../resources/compression-rules.md' before producing output.`
- **Why it's a FP**: This is a relative path *within the skill package* — the skill's `agents/` subdirectory references a `resources/` sibling. The path does not traverse outside the skill's root. SD-003's regex catches any `../` reference, but legitimate skill packages routinely organize files across subdirectories and reference them via relative paths.
- **Proposed fix**: SD-003 should only flag `../` references that escape the nearest `.claude/` or `.codex/` skills root — i.e., require at least two levels of `../` to leave the skill boundary, or check that the resolved path leaves the skill package directory.

### FP-7: SD-008 MEDIUM fires on a Bash permission string in `settings.local.json`

- **Rule**: SD-008 (Base64 Obfuscation)
- **Target**: skill-detector (self)
- **File**: `.claude/settings.local.json:51`
- **Actual content**: `"Bash(cat /Users/glibrulev/projects/skill-detector/testdata/malicious/exfiltration/*.sh)"`
- **Why it's a FP**: The base64 detector matched the substring `detector/testdata/malicious/exfiltration/` (45 chars of `[A-Za-z0-9/]`) as a potential base64 string. This is a filesystem path, not encoded data.
- **Proposed fix**: The base64 regex should require the matched string to end with `=` or `==` padding, or must be parseable as valid base64 (all 4-character groups), or must be at least 60+ chars. A 45-char run of alphanumeric+slash in a file path is not obfuscation.

### FP-8: SD-007 HIGH fires on `.goreleaser.yml` homepage URL

- **Rule**: SD-007 (Outbound Network Call)
- **Target**: skill-detector (self)
- **File**: `.goreleaser.yml:45`
- **Actual content**: `homepage: "https://github.com/velzepooz/skill-detector"`
- **Why it's a FP**: A Goreleaser Homebrew cask definition. The `homepage` field is metadata shown in `brew info`, not a network call. Confidence was MEDIUM, which boosted this above the fold.
- **Proposed fix**: `.goreleaser.yml` and similar CI/release config files (`.releaserc`, `Makefile`, `Dockerfile`) should be excluded from SD-007 or have confidence clamped to LOW unless the URL is in a `run:` or `exec:` context.

### FP-9: SD-003 HIGH fires on `/usr/bin/xattr` in `.goreleaser.yml`

- **Rule**: SD-003 (Path Traversal)
- **Target**: skill-detector (self)
- **File**: `.goreleaser.yml:56`
- **Actual content**: `system_command "/usr/bin/xattr", args: ["-dr", "com.apple.quarantine", ...]`
- **Why it's a FP**: This is the Homebrew cask code-signing exemption command (`xattr -dr com.apple.quarantine`), a required and well-known macOS distribution step. Using the full path `/usr/bin/xattr` is the safe convention (avoids PATH hijacking).
- **Proposed fix**: Paths like `/usr/bin/`, `/usr/local/bin/`, `/bin/`, `/sbin/` referring to well-known system binaries should be classified as LOW confidence by SD-003. Matching `/usr/bin/<known-binary>` as a path traversal is spurious.

## Rationale clarity issues

**RC-1**: SD-003 on `.goreleaser.yml` — description reads `"path traversal pattern detected — access outside skill directory"` but the target is not a skill; it's a release config. The phrase "outside skill directory" implies a skill context that doesn't apply. For non-skill targets this message is confusing to a reviewer.

**RC-2**: SD-007 on `README.md` — description `"outbound network reference to https://img.shields.io/…"` with severity HIGH is alarming. A staff engineer reviewing this report would immediately identify it as a badge URL and lose confidence in the tool. The HIGH severity label needs to be qualified or the confidence should auto-reduce for documentation files.

**RC-3**: SD-008 on `settings.local.json` — description `"long base64-encoded string detected — potential obfuscation"` when the matched token is clearly a filesystem path is confusing. The remediation says "Avoid embedding base64-encoded data" which makes no sense in context.

**RC-4**: SD-012 on brainstorming doc — description `"post-install or lifecycle hook detected"` in a `.md` file is misleading. The message implies an active lifecycle hook when the file is plaintext documentation.

All other rationales (SD-015, SD-016, SD-017, SD-018, SD-019, SD-020, SD-021, SD-004 on actual credential scripts) are clear and actionable for Maya.

## Conclusions

The SP-1 engine is functionally correct: all 5 CVE fixtures fire their expected rules, all 8 clean fixtures score A/A/A/A, and the core detection rules (SD-015 through SD-021 covering the settings.json + CLAUDE.md attack surface) work precisely. The false-positive analysis reveals two structural issues for SP-2:

1. **Context blindness in documentation files**: SD-007, SD-008, SD-012, SD-013, and SD-004 all fire on `.md` prose that *discusses* threat patterns rather than *implementing* them. The fix is either file-type gating (`.md` files get LOW confidence by default for most rules) or requiring a second corroborating signal before elevating to MEDIUM or HIGH confidence.

2. **Package ecosystem noise**: `package-lock.json` and `node_modules/` generate hundreds of SD-007/SD-008 findings in any JavaScript/TypeScript project. Adding these to the default exclusion list (alongside `.git/`) is the single highest-leverage improvement for real-world scan UX.

Neither issue blocks ship for v0.2.0 — the tool's threat detection is sound. The noise will erode trust with users who scan real repos, so SP-2 should prioritize these two fixes as the first implementation stories.

Future dogfood pass (SP-2): re-run against 3 external public repos (e.g., a popular Claude skill package from the community, a random Next.js starter, a Go CLI tool) after the exclusion list fix is shipped, to validate noise reduction.
